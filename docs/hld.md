# High Level Design — Spice Garden OMS

System design at the component level: scale, topology, failure, and the
trade-offs behind each choice. Module-level detail is in [lld.md](lld.md).

---

## 1. Requirements

### Functional

- Staff create orders with line items and a customer.
- Orders move through a fixed lifecycle. Illegal moves are rejected.
- Kitchen sees new orders without refreshing.
- Staff search and filter orders.
- Managers see operational and financial numbers.

### Non-functional

| Need | Target | Why this number |
|---|---|---|
| Read latency | p95 < 200 ms | A waiter tapping a screen mid-service |
| Write latency | p95 < 300 ms | Order creation is blocking work |
| Live update lag | < 1 s | Kitchen must see an order as it lands |
| Availability | 99.9% (≈ 45 min/month) | Restaurant hours only. Not a payment system |
| Durability | No lost order, ever | An order is money and a hungry customer |
| Consistency | Strong for order state | Two cooks must never both own one order |

## 2. Scale — the numbers that justify everything

This is the section most designs skip. Without it, every choice is a guess.

**Assumed business:** 20 locations, 150 orders per location per day.

| Metric | Value | Working |
|---|---|---|
| Orders / day | 3,000 | 20 × 150 |
| Orders / year | ~1.1 M | 3,000 × 365 |
| Peak order rate | **~0.3 / sec** | 60% of orders land in 5 service hours, 3× burst |
| Status changes / day | 12,000 | 4 per order |
| Concurrent staff | ~300 | 15 per location |
| Open SSE connections | ~100 | kitchen + manager screens |
| Peak read rate | **~50 req/sec** | 300 staff × 10 requests/min |
| Data / year | ~3 GB | 1.1 M orders + 3.3 M items + 4.4 M events, with indexes |

### The conclusion

**Peak write load is under 1 write per second. A single Postgres instance on a
small box handles thousands.** We are roughly **100× under capacity** on writes
and **20× under** on reads.

So the design decision is not "how do we scale this". It is **"how do we avoid
building things this system does not need"**. Sharding, read replicas, CQRS, a
service mesh, and eventual consistency all cost correctness and cost debugging
time, and buy nothing at 0.3 writes per second.

Redis and the worker are here for **latency isolation and fan-out**, not
throughput. That distinction matters: Redis is not caching because Postgres is
slow — it is caching so a dashboard poll doesn't run eight aggregate queries.

## 3. Architecture

```
        ┌──────────────────────────────────────────┐
        │  React SPA (Vite)                        │
        │  Orders · Kitchen · Dashboard · Staff    │
        └──────┬───────────────────────┬───────────┘
               │ HTTPS/JSON            │ SSE (one long-lived GET)
               │ Bearer JWT            │
        ┌──────▼───────────────────────▼───────────┐
        │  Hono API  (Node, stateless, N replicas) │
        │  ┌────────────────────────────────────┐  │
        │  │ auth → validate → route → serialize│  │
        │  └────────────────────────────────────┘  │
        └───┬──────────────┬───────────────┬───────┘
            │ SQL          │ pub/sub       │ enqueue
            │              │ + cache       │
     ┌──────▼──────┐  ┌────▼─────┐   ┌─────▼──────────┐
     │ PostgreSQL  │  │  Redis   │   │ BullMQ Worker  │
     │ system of   │  │ optional │   │ notifications  │
     │ record      │  │          │   │                │
     └─────────────┘  └──────────┘   └───────┬────────┘
                                             │
                                    console │ twilio (pluggable)
```

### Component responsibilities

| Component | Owns | Stateless? |
|---|---|---|
| React SPA | UI, local form state, one `EventSource` | yes |
| Hono API | validation, authz, business rules, serialization | **yes** — no session, no in-memory order state |
| PostgreSQL | **the only source of truth** | no |
| Redis | analytics cache, SSE fan-out between API replicas, queue backing | no, but **disposable** |
| Worker | outbound messages, retries | yes |

**The API holding no state is what allows N replicas behind a plain load
balancer.** The only cross-replica coordination is SSE fan-out, and Redis
pub/sub handles that — so no sticky sessions.

## 4. Critical paths

### 4.1 Create order

```
POST /orders
  ├─ JWT verified              (no DB hit — claims are in the token;
  │                             one Redis SISMEMBER for revocation, see §9)
  ├─ Zod validates the body    (reject before touching Postgres)
  └─ ONE TRANSACTION
       ├─ claim the idempotency key      (unique index = the lock)
       ├─ find customer by id, else by phone, else insert
       ├─ insert order   (order_number from a Postgres sequence)
       ├─ insert items   (total_price generated by the DB)
       ├─ insert order_status_events  (null → CONFIRMED)
       ├─ insert notifications outbox row
       └─ store the response body against the idempotency key
     COMMIT
  ├─ enqueue notification job     ─┐ after commit —
  └─ emit order:created            ─┘ failures here cannot corrupt the order
```

**Why the split at COMMIT:** everything that must be atomic is inside. Everything
that can be retried is outside. If the process dies between commit and enqueue,
the outbox row is still `PENDING` and a periodic drain picks it up.

### 4.2 Status transition — the concurrency case

Two cooks tap "Start prep" on the same order at the same moment.

```
UPDATE orders SET status='PREPARING', assigned_staff_id=$staff
WHERE id=$id AND status='CONFIRMED' AND assigned_staff_id IS NULL
```

- Postgres serializes the two updates on the row lock.
- First one: 1 row changed. Second one: **0 rows changed** — the `WHERE` no
  longer matches.
- 0 rows *is* the conflict signal. No `SELECT … FOR UPDATE`, no version column,
  no lock held across a network round trip, no deadlock ordering to reason about.

**This is the single best design detail to explain in an interview.** It shows
you know optimistic concurrency falls out of SQL for free when the guard is in
the `WHERE` clause.

### 4.3 Live update fan-out

```
API replica 1: status changes ──▶ Redis PUBLISH order:updated {id}
                                        │
              ┌─────────────────────────┼─────────────────────────┐
              ▼                         ▼                         ▼
      replica 1 SUB              replica 2 SUB             replica 3 SUB
      → its open SSE             → its open SSE            → its open SSE
```

Each replica pushes only to the browsers connected to *it*. Redis is the bus.

**Frames carry an order id, not the order body.** The browser refetches. Costs
one extra request, buys two things: authorization stays on the fetch path (a
stream that outlives a token can't leak orders), and payload shape lives in one
place.

## 5. Consistency model

Different parts need different guarantees. Saying so explicitly is the point.

| Data | Guarantee | Reasoning |
|---|---|---|
| Order + items + status | **Strong / ACID** | One Postgres, one transaction. Money and food. |
| Status history | **Strong, same transaction** | The log can never disagree with the order it describes |
| UI state | **Eventually consistent, < 1 s** | SSE push, plus refetch on navigation as the backstop |
| Notifications | **At-least-once** | Outbox + retries. A driver cannot dedupe — a sent SMS is sent. Duplicates are minimised at the *claim*: the worker takes a row with `UPDATE notifications SET status='SENDING' WHERE id=$1 AND status='PENDING' RETURNING *`, so only one worker ever sends it. A crash between send and `SENT` can still repeat one message; for order-status text that is the right trade against dropping it |
| Analytics | **Stale up to 30 s** | Cache TTL. Nobody makes a decision on 30-second-old revenue |

**Deliberate:** we never chose eventual consistency where strong was available.
The single-node database *is* the simplifying assumption, and §2 justifies it.

## 6. Failure modes

| Failure | Blast radius | Behaviour | Recovery |
|---|---|---|---|
| **Redis down** | none | Cache misses go to Postgres. SSE degrades to same-replica only. Jobs run inline after the response. One warning logged. | Reconnects on its own |
| **Worker down** | notifications only | Outbox rows stay `PENDING`. Orders unaffected. | Drain on restart sends the backlog |
| **One API replica down** | its open SSE connections | Browser `EventSource` reconnects automatically to another replica | LB health check |
| **Postgres down** | **total outage** | API returns 503. No writes, no reads. | See below |
| **Twilio failing** | notifications only | 3 retries with backoff, then `FAILED` with the error recorded | Manual replay |
| **LLM API failing / no key** | one dashboard panel | `narrative: null`. Every real number still renders. | — |

### The honest weak point

**Postgres is a single point of failure.** For this scale that is the right
call — a hot standby doubles the operational surface to protect against an
outage during a 5-hour daily service window.

The production answer, in order of cost:

1. Automated backups + point-in-time recovery. RPO ≈ 5 min, RTO ≈ 30 min.
2. A synchronous streaming replica with automatic failover. RPO 0, RTO < 1 min.
3. Managed Postgres (RDS Multi-AZ / Cloud SQL HA) — buys #2 without running it.

For a chain where a 30-minute outage means writing orders on paper, #1 is
proportionate. I would move to #3 at the point where a second region is opened.

## 7. Scaling path — what breaks first

Ordered by when it actually bites, not by how interesting it is.

| Scale | What breaks | Fix |
|---|---|---|
| **10×** (30 k orders/day) | `ILIKE '%…%'` search does a full scan | `pg_trgm` + GIN index on the searched columns |
| **10×** | Analytics aggregates scan millions of event rows | Hourly rollup table, written by the same worker |
| **25×** | Derived `SUM()` totals on list pages get expensive | Materialized view refreshed off the event stream — *still* not stored columns with triggers |
| **50×** | 100+ API replicas each holding a Redis pub/sub connection | Dedicated SSE process; API publishes only |
| **100×** (300 k orders/day) | Read load on the primary | Read replicas for list, search, and analytics |
| **100×** | Table size ~300 GB | Partition `orders` and `order_status_events` by month; archive cold partitions |
| **500×** | Write load approaching a single primary's limit | Shard by `location_id` — locations are a natural, never-joined boundary |

**Note what is not on this list:** microservices. Nothing here needs an
independent deployment or scaling unit. Splitting this into services would add
network calls and distributed transactions to solve a problem we don't have.

## 8. Trade-offs

| Decision | Chosen | Rejected | Why | Revisit when |
|---|---|---|---|---|
| Totals | Derived `SUM()` | Stored columns + triggers | Stored totals need two mutation paths kept in sync and can silently drift. Derived cannot be wrong. | List queries measure slow → materialized view |
| Concurrency | Conditional `UPDATE` | `SELECT … FOR UPDATE`, version column | One statement, no held lock, no deadlock ordering. Conflict detection is free. | Multi-row atomic updates appear |
| Prep timestamps | Derived from event log | Columns on `orders` | One source of truth, survives repeated transitions | Rollups need them denormalized |
| Real-time | SSE | WebSockets, polling | Updates are one-way. Browser reconnects natively. Zero extra dependency. | Client needs to push |
| Live payload | Order id | Full order body | Keeps authz on the fetch path, one serializer | Bandwidth becomes a concern |
| Notifications | Outbox + queue | Direct send in the request | External latency and failure never touch the HTTP path, and nothing is lost after commit | — |
| Cache | Analytics only | Caching order lists | Order lists change on every status click and are already pushed live. Caching them = pure invalidation cost. | Read replicas exist |
| Auth | Stateless JWT | Server sessions | Keeps API replicas stateless, no session store | Fine-grained revocation needed |
| Database | One Postgres | Postgres + Mongo/Elastic | The data is relational and small. A second store means dual writes. | Search or analytics outgrows §7 |
| Deployment | Modular monolith | Microservices | 0.3 writes/sec. Services buy independent scaling nobody needs. | Teams, not load, force a split |

## 9. Security

| Concern | Control |
|---|---|
| Identity | JWT HS256, 12 h TTL, `{ sub, role, name }` |
| Passwords | Argon2id, per-user salt |
| Authorization | `requireRole` middleware on the route, never `if` in a handler |
| **Revocation** | Deactivating staff writes their id to a Redis set checked per request (sub-ms). Without Redis, the 12 h TTL is the exposure window. **Stated, not hidden.** |
| SQL injection | Parameterized everywhere via Drizzle. Zero string-built SQL |
| Input | Zod at the edge; DB constraints as the second wall |
| Transport | TLS terminated at the proxy |
| PII to the LLM | **Aggregates only.** Never customer rows, names, or phone numbers |
| Secrets | Environment only. Boot fails loudly if `JWT_SECRET` is missing |

### About `AUTH_DISABLED`

It exists so a reviewer can verify the assignment contract without first
obtaining a token. It is a real risk, so it is fenced:

- The server **refuses to boot** with it set when `NODE_ENV=production`.
- It logs a loud warning on every startup.
- It is documented in `readme.md` and `questions.md`, not hidden in a corner.

A flag that can't reach production and announces itself is a reviewer
convenience. A flag that silently defaults on would be a vulnerability.

## 10. What I would do differently at real scale

Worth saying out loud — it shows the current design is a choice, not a ceiling.

- **Managed Postgres with HA** before anything else. Highest availability gain
  per unit of effort.
- **Move analytics off the primary** to a read replica, then to hourly rollups.
- **`location_id` on `orders` from day one** if multi-location were in the
  contract. Retrofitting a tenant key is painful; adding it early is one column.
- **Separate the SSE process** once replica count makes fan-out connections
  noticeable.
- **Structured logs with a request id** propagated to the worker, so an order
  can be traced end to end.
- **Keep the monolith.** Split only when team boundaries — not load — demand it.
